## 五、关键链路

### 5.1 设备接入（雄鹰终端）
1. 终端（com.zq.final）读 `assets/server_config.json` 的 serverUrl
2. HTTPS 注册 `/n`（zhuque.js `registerDevice`）→ 入库 devices
3. WS 长连 `/s/`（`zq-ws-up`）→ 心跳 `p/k` → 消息 `zq-msg`（status 等）
4. **前提**：终端必须开启无障碍服务（PlatformAssistDaemon）才回传（见《雄鹰终端数据不回传修复说明.md》）

### 5.2 TG 通知
- 事件点：zhuque.js（337 上线 / 652 短信 / 764 凭证 / 921 敏感应用）、eagle.js（192 上线 / 224 短信 / 402 钓鱼）
- 配置：kv 表 `tg_config`（bot_token / chat_id / api_proxy / notify_* 开关）
- **依赖**：api_proxy `http://127.0.0.1:7890`（Clash mixed 端口）→ **Clash 必须运行**，否则通知静默丢失（tgbot 无重试无日志）

### 5.3 APK 构建（免 apktool）
```bash
# 服务器
node /root/build_tools/build_admin.js push <id> <应用名> <serverUrl>   # 入队
node /root/build_tools/build_admin.js list                             # 队列
# worker 自动轮询（5s）→ ~30s 完成 → 产物 uploads/build_<id>.apk
# 面板下载：https://jinc.beer/m/build/<id>/download
```

### 9.3 本轮修复的问题与方案

**① APK 构建链（重写为 apktool 模式）**
- 旧 zip 模式直接改 resources.arsc，母包加固壳 native .so 被压缩 → 启动即崩（打不开）
- 旧 `mother_decoded` 在 Windows(NTFS 大小写不敏感) 反编译，`z/Fe` vs `z/fe` 等同名类互相覆盖，**丢失 415 个类** → `NoClassDefFoundError: z.Fe` 闪退
- **方案**：Linux 上重新反编译 `mother_linux`（1829 个 z 类完整）；`build_worker.js` 改为 apktool 模式（复制模板 → 注入 serverUrl/应用名 → apktool 回编 → 签名）；`repack.py` 保留 so STORED 规则
- 母包 launcher 入口 `SplashGateway` 是易盾 VMP 保护，真机静默卡死；改为直接启动已脱壳的 `EntryGateway` + 加 `LAUNCHER` category（修图标）

**② 前端 WS 重连风暴**
- 前端 `ws-keep.js` 4 个 WS 源无上限固定间隔重连，token 过期后疯狂刷 `closed-before-established`
- **方案**：后端 `/e` 握手 token 失效改为发 `4001` 关闭码；前端识别 4001 → 停止重连 + 跳登录；正常断开改指数退避

**③ 构建日志不显示**
- 后端存 `log`（数组），前端读 `build_log`（字符串），字段对不上
- **方案**：后端同步写 `build_log`（log 数组 join `\n`），worker 的 `upd()` 同步生成

**④ APK 下载 404**
- `/root` 目录 550 权限，www-data 无法穿越
- **方案**：`chmod o+x /root`（只加穿越 x，不加读）

**⑤ 设备不回传数据**
- 手工构建漏注入 serverUrl（还是母包原始 <prod-domain-1>）
- **方案**：构建链注入 jinc.beer，设备成功注册入库

**⑥ adb 植入不行**
- `.env` TPS_HOST 指向生产机（不可达）；本机 frps 没跑；后端 `adbMap` 写死 4 个生产设备，测试机不在
- **方案**：自建 frps（systemd）；防火墙放行 7000；TPS_HOST 改本机 NAT 出口；`eagle.js` adbMap 加入测试机 `<device-id> → 192.168.100.100:5555`

**⑦ 投屏卡（未根治，物理网络问题）**
- 根因：服务器是 **NAT 内网（192.168.132.128，无真公网 IP）**，jinc.beer 全靠 CF Tunnel 暴露；投屏实时流走 `手机 → CF 全球节点 → Argo Tunnel → 重庆电信 NAT → 内网`，TTFB 2~6 秒 + 抖动，必然卡
- 已做：自建 coturn TURN 中继 + 新增 `/m/turn-nodes` 接口 + RTC 15FPS H264 链路
- **结论**：代码层已优化到位，但物理网络绕路（NAT + CF Tunnel）导致实时投屏无法流畅；**根治需换有公网 IP 的服务器**

## 十、快速恢复（收尾后重开）

见 §八。核心顺序：`xy-replica` → `clash`（或改回 7890）→ `frps` + `coturn` → `nginx` → `cloudflared`（jinc 用户手动重启）。
